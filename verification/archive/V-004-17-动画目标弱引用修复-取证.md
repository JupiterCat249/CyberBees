## 一、现象与诊断（读控制台）

人反馈：**点击「开始对局」后卡死**。控制台：

```
game_status.break.reason: "Trying to assign invalid previously freed instance."
editor_errors: _step: Trying to assign invalid previously freed instance. (battle_anim.gd:140)
```

**与 V-004-16 是同一类错误，但行号变了**（158 → 140）✗ —— 说明上一轮的修复**没打到根上**。

## 二、真正的根因（两层）

| 层 | 问题 |
|----|------|
| 表层（V-004-16 已修） | `queue_free()` 后**帧末才真释放**，`is_instance_valid()` 期间仍为 true → 写属性报错；已加 `is_queued_for_deletion()` 守卫 |
| **深层（本轮定位，才是真凶）** | 我把**节点强引用存进了字典**：`_running[name] = {"target": target}` ✗ —— 节点被 free 后，**从字典里取出并赋给变量这一步本身**就会报 `assigning invalid previously freed instance` ✗✗ —— **发生在任何守卫之前**，故上一轮的守卫根本来不及生效 ✗ |

## 三、修复（走 MCP · 4 处）

**核心：字典只存弱引用（`weakref`），已释放则 `get_ref()` 返回 `null`，天然可判死**

| 位置 | 改动 |
|------|------|
| `action()` | `_running[name] = {"i":0,"c":0,"f":0, **"tref": weakref(target)**}` |
| `_step()` | `var tg = st["tref"].get_ref()` → `null` 即 `_running.erase(name)` 丢弃；再判 `is_instance_valid / is_queued_for_deletion` |
| `_apply_clip()` | 同上从 `tref` 解析；`null`/无效/待释放 → 直接 return |
| `stop()` | 目标也从 `tref` 取（可能已释放）|

## 五、教训（**这条最关键**）

1. **Godot 中"持有节点引用"本身就是危险动作** ✗ —— 一旦对象被 `free`，
   **对该引用的读取/赋值/传参**都可能抛 `invalid previously freed instance`，
   **而不是等到真正使用它做操作**。守卫写在"使用点"来不及 ✗
2. **正确做法**：跨帧持有的节点引用**一律用 `weakref()` 存**，取用时 `get_ref()`（已释放 → `null`）✅
3. **同一错误在不同行号重复出现**，说明上一轮只修了表层 ✗ —— 应顺着"这个引用是怎么被持有的"往上找，
   而不是在报错行加判空 ✗
4. 本类错误会让 Godot **停在调试器断点**（视觉上 = 卡死），
   排查入口首选 `logs_read(source='game')` 的 `game_status.break.reason` ✅
