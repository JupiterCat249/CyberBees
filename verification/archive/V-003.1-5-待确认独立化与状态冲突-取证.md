# V-003.1-5 「待确认」独立化 —— 多状态互相冲突的根治 · 验证取证

> 状态：已封存（验证用，非生产文件）
> 对应迭代·检查点：迭代003.1 · 检查点 1/2（输入/状态耦合根治）
> 封存日期：2026-08-27

## 人提供的决定性证据

> "在启用支援判定的单位上，反复点击目标试图触发判定时，系统最终显示的是**不断输出待确认而非确认**"
> "详细浮窗：第一次长按且没有其他操作时可正常启动，但一旦触发支援技能判定则无法显示详细信息"
> **"本次故障更像是多个状态间互相冲突，为此可能要改进输入处理机制"** —— 诊断正确。

## 两条根因

### 根因 A：`clear_sel()` 连带清除待确认

`clear_sel()` 内部调用了 `clear_pending()`，而 `clear_sel()` 在 `battle_state.gd` 中有 **16 处**调用点
→ 任何一次"顺手清选中"都会杀掉待确认 → `confirm()` 每次都走"新建待确认"分支、
**匹配永不成功** → 日志不断输出「待确认」 ✗（与人观察完全一致）。

**修复**：待确认改为**独立状态**，`clear_sel()` 不再连带清除；
只在明确语义下清除 —— 执行（`confirm_pending_at`）· 取消（`on_click_empty`）· 改选（`select_unit_at`）。

### 根因 B：待确认的执行依赖其他状态（选中/模式）

即使待确认保留，若选中单位被冲突清掉，下一次点击会落入"改选"分支 ✗。

**修复**：`on_cell_clicked()` 增加 **最高优先分支** ——
`if pending_kind != "" and pending_cell == cell: confirm_pending_at(cell)`，
**完全不依赖 mode / 选中是否仍在**；并在 `confirm()` 时把施放者记入 `preview["source_id"]`，
执行时若选中已丢失则补回。

## 验证（实机 eval，注入状态冲突重演故障）

| 步骤 | 结果 |
|------|------|
| 1) 选中叶蜂 → 点自身进支援模式 | `mode=3` |
| 2) 点目标 | `pending=支援` |
| **[注入 clear_sel]（重演冲突）** | `pending=支援` **保住** ✅（修复前被清空）、`selected_unit=-1`（被冲突掉） |
| 3) 再点同格 | `pending=[]`，泥蜂 `atk=4` `effects=["atk_up"]`，叶蜂 `acted=true` ✅ |
| 日志 | `泥蜂 获得效果「攻击提升」` / `技能「鼓舞」生效（命中 1 处）` / `叶蜂 支援 泥蜂` |

## 浮窗「一旦触发判定就再也弹不出」

原因是长按允许条件含 `mode == IDLE`，而支援模式下 `mode = SUPPORT_TARGET` →
长按被永久禁止（直到离开模式）。本轮已把 `selected_unit < 0` 从条件中移除，
但**「模式选择中禁止长按」是刻意保留**（否则浮窗会抢走确认点击）。
后续若要让"模式中也能长按详情"，需先解决浮窗与确认点击的优先级冲突（见改进项）。

## 改进项（下一轮：输入处理机制重构）

当前"点击"要同时裁决：长按详情 / 待确认执行 / 模式目标选择 / 改选 / 取消，耦合较深。
建议改为**显式交互状态机**：单一 `InteractionState`（IDLE / CONFIRM / MODE_TARGET / LONG_PRESS_PENDING）
+ 一张明确的优先级表，每帧只由该状态决定如何处理一次点击，禁止各处分散地清状态。
