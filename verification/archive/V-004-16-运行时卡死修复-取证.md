## 一、诊断（读控制台输出）

**游戏日志**（`logs_read(source='game')`）显示运行中断状态：

```
game_status.break.reason: "Trying to assign invalid previously freed instance."
editor_errors: _apply_clip: Trying to assign invalid previously freed instance.
                                                  (res://scenes/battle/battle_anim.gd:158)
```

`battle_anim.gd:158` = **`U.MOVE_BY` 分支的 `(tgt as Node2D).position += step`** —— 正在给一个**已被释放的节点**写位置 ✗。
Godot 遇到此类错误会**停在调试器断点** → 表现为**游戏卡死**（人实机所见一致）。

## 二、根因

`battle_board_view.gd:72 / 101` 在**重建单位节点**时执行 `n.queue_free()` ✗；
而动画引擎 `_running` 表里仍持有该节点引用 ✗ → 下一帧 `_step → _apply_clip` 继续写它的 `position` ✗。

**为什么原有的 `is_instance_valid` 守卫没拦住**：
`queue_free()` 只是**标记**，节点要到帧末才真正释放 —— 在此之前 `is_instance_valid()` 仍为 `true`，
但**对它的属性赋值会触发 "invalid previously freed instance"** ✗。

## 三、修复（走 MCP）

**两处守卫**（`battle_anim.gd`）：

```gdscript
# _step() 开头：目标已被释放 / 已被 queue_free → 丢弃该动画（从运行表移除）
var tg: Node = st.get("target", null)
if tg != null and (not is_instance_valid(tg) or tg.is_queued_for_deletion()):
    _running.erase(name)
    return

# _apply_clip() 开头：同样补 is_queued_for_deletion()
if tgt == null or not is_instance_valid(tgt) or tgt.is_queued_for_deletion():
    return
```

设计取舍：**丢弃**而非"等它释放"—— View 重建节点意味着旧节点的表现已无意义，丢弃符合"终止不复位、不写已死目标"的语义 ✅

## 六、教训（写入系统维护文档）

1. **持有节点引用做逐帧写入时，必须同时判 `is_instance_valid` 与 `is_queued_for_deletion`** ✗
   —— `queue_free()` 后到帧末之间，`is_instance_valid` 仍为真，但赋值会报
   "invalid previously freed instance" 并**把游戏停在断点（卡死）**
2. **View 重建节点与动画系统之间必须有明确的生命周期约定**：动画遇到"目标待释放"应**丢弃**而非继续写
3. **实机卡死优先读 `game_status.break.reason`** —— 它直接给出错误文本与脚本行号，比翻日志快得多
