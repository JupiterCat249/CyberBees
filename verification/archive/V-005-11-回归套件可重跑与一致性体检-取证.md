## 四、⚠️ 过程中的关键发现（比套件通过本身更重要）

**首轮在"同进程连续跑多个套件"时，套件2 给出假阴结果**：
```
①过滤开 精确打击: hits=3 | 中心敌20 相邻己20 相邻敌15   ← 中心敌没掉血（错）
②不过滤 巡航导弹: hits=3 | 中心敌20 相邻己20 相邻敌16   ← 只掉 1 个（错）
```

**定位过程**（诊断 `game_eval`）：
```
units=10                       ← 正常一局应约 4~5 个，10 说明累积了两局
id=9/10/11 = 本局 spawn 的泥蜂（cell 2,2 / 2,1 / 2,3）
resolve_targets 目标数量=3      ← 目标格解析正确
run_skill hits=[id 5(cell 2,1), id 4(cell 2,2), id 8(cell 2,3)]  ← **命中的是更早的 id**
after id=9/10/11 hp=4/4/4      ← 本局单位毫发无伤
```

**根因**：`BattleSetup.prepare()` 只重置手牌/费用/阶段/地图，**不清空 `units` 与 `next_id`**；
同格上同时存在"上局单位"与"本局新单位" → `unit_at(cell)` 命中的是**更早的旧 id** → 伤害打到"看不见的旧单位"上。

**处置与结论**：
- 重启进程（干净内存态）后**三个套件全部通过** → **游戏逻辑正确，套件期望正确**，这是**运行时/测试态问题**；
- 已作为「铁律」写入 `suites/README.md`（跑套件前必须重启进程；"最近验证"行记录 `run_token`）；
- 生产侧影响：正常玩法下 `start_battle()` 每进程只调一次（无游戏内"再来一局"入口）→ 当前无玩家可见影响；
  **若未来加入"再来一局"，必须先清空 `units`/`next_id`** —— 已在《当前状态》与迭代记录中登记为后续注意项。

**方法教训**：套件输出"看起来像功能坏了"时，先怀疑**测试态污染**（单位/状态残留），
不要急着改生产代码 —— 本轮用"进程总数 + resolve_targets vs actual hits 对照"三步即定位 ✅
