## 二、真实根因（**代码结构缺陷，非 RichTextLabel 之过**）

查看 `ad6c4f4` 的 52–103 行：

```gdscript
func _on_state_changed() -> void:
	_labels["info"].text = …
	<迭代004 C 步加进来的"整条染色 + _ensure_turn_bg() 调用">

## 确保回合背景条存在…
func _ensure_turn_bg() -> void:
	if _turn_bg != null and is_instance_valid(_turn_bg):
		return
	if overlay == null:
		return
	_turn_bg = ColorRect.new()
	… 创建 TurnBg …
	overlay.move_child(_turn_bg, 0)
	if state.winner != "":                    ← ⚠️⚠️ 这里开始
		_labels["btn"].text = "游戏结束"          ← BtnText / LogText / HelpText
	elif …                                     ← 的全部赋值代码
	_labels["log"].text = …                    ← **被误并入 _ensure_turn_bg() 内部**
	_labels["help"].text = …                   ← ⚠️⚠️ 到这里结束
```

**根因**：在我做 **C 步（检查点10 · 回合背景色）** 时，补丁把 `_ensure_turn_bg()` 的函数定义
**插进了 `_on_state_changed()` 的中间**，导致其后**原有的主按钮/日志/帮助赋值代码被"吞进"了新函数体内** ✗

**后果**：`BtnText/LogText/HelpText` 的更新**只依赖于 `_ensure_turn_bg()` 是否被调用** ✗
- `ad6c4f4`（C 步版本）在 `_on_state_changed()` 中**调用了**它 → 三处文本正常 ✅
- 而我后续两次改动**移除了该调用**（一次为改 RichTextLabel，一次为移除阵营底色）→
  **三处赋值从未执行** → 主按钮与日志**全空** ✗ —— **两次事故由此而来** ✅

> 结论：**RichTextLabel 与"行内染色"本身没有问题**（`V-004-25` 中 `InfoRich` 的文本与染色完全正确 ✅）；
> 真正的元凶是**这个被误合并的函数** —— 它让"HUD 更新"与"创建背景条"形成了**隐藏的强耦合** ✗

## 五、方法教训（比缺陷本身更重要）

1. **"回退即好"是极强的定位线索** ✅ —— 说明问题**就在被回退的那段改动范围内**，
   应当**立刻 diff 该范围**（本轮我第 3 次才做，浪费了两轮 ✗）
2. **UI 改动必须"全屏逐节点核对"**（`game_eval` 列 `text/visible` 比截图可靠 ✅）
3. **改动后必须读控制台**（本轮控制台是干净的 —— 说明**不是异常**，而是**逻辑未执行** ✗，
   这一点当时没有及时利用来缩小范围 ✗）
4. **打补丁时函数边界必须核对**：`old_text` 若只覆盖函数开头、`new_text` 又新增了函数定义，
   极易把**后续语句误并入新函数** ✗ → 补丁后必须 `grep -n '^func '` 核对函数边界 ✅
5. **隐藏耦合要及时拆**：任何"只在某条路径被调用时才更新"的 UI 赋值都是隐患 ✗
