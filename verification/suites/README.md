# verification/suites/ —— 可复用验证套件（非生产文件）

> 状态：已封存（验证用，非生产文件）
> 最后更新：2026-08-28

## 为什么有这一层

此前验证代码都是**内联写在 `game_eval` 调用里**（用后即散，且改一处要重打字、易错）。
本目录把验证代码**落盘为可复用套件**：需要时**读取文件 → 作为 `game_eval` 的 code 直接执行**，
保证「同一套验证可反复跑、可对比历史结果」。

## 规范

1. **命名**：`V-suite-<主题>.gd.txt`
2. **后缀必须是 `.gd.txt`**：目录含 `.gdignore`，且**禁止 `.gd`**（否则 Godot 会当脚本加载 → Parse Error → 卡断点，已实际踩过）
3. **文件头部**必须标注：
   ```
   > 状态：已封存（验证用，非生产文件）
   > 对应迭代·检查点：
   > 最近验证：YYYY-MM-DD 结果
   ```
4. **正文即 `game_eval` 的代码**（可直接复制粘贴执行）；不要写 Markdown 以外的装饰，避免粘贴时带入
5. **测试数据一律运行时生成**（`spawn` 构造单位），不写入生产场景/资源

## 如何重跑（2026-08-28 补充 · 迭代005 D3）

```
① 前置：**重启游戏进程**（见下方"铁律"）—— 编辑器中 stop → run（run_token 递增即新进程）
② 取正文：套件文件头部以 `>` 开头的行是 Markdown 说明，**从第一条非 `>` 行开始才是可执行 GDScript**
   （例：`sed -n '10,$p' V-suite-技能系统四路径回归.gd.txt`）
③ 执行：把正文作为 `mcp__godot-ai__editor_manage(op="game_eval")` 的 `code` 参数
④ 判读：输出中每行末尾的"（应 …）"即期望值；逐行对照，全部一致 = 通过
⑤ 记录：把"最近验证"行更新为本次日期 + 结论
```

### ⚠️ 铁律（2026-08-28 实测教训，必读）

**同一游戏进程内重复调用 `start_battle()` 会保留历史单位** —— `BattleSetup.prepare()` 只重置手牌/费用/阶段/地图，
**不清空 `units` 与 `next_id`**。于是：

- 同一格上会同时存在"上一局的单位"与"本局新 spawn 的单位"；
- `unit_at(cell)` / `resolve_targets()` 拿到的是**更早的 id**（旧单位）→ 伤害打到了"看不见的旧单位"上；
- 现象极具误导性：**"只有 1 个单位掉血"、"命中数=2 而不是 3"**，看起来像溅射/过滤功能坏了 ✗

**因此：跑任何套件前先重启游戏进程**（或至少保证本进程内只 `start_battle()` 一次）。
本目录套件**全部要求干净进程**，其"最近验证"行中的 `run_token` 即当次进程号。

> 注：这是**运行时/测试态**问题，不是生产缺陷 —— 正常玩法下 `start_battle()` 每进程只调用一次（无游戏内重启入口）。
> 若未来加入"再来一局"，**必须在 `prepare()` 里先清空 `units` / `next_id`**（已在《当前状态》记为后续注意项）。

## 附带体检：卡池 ↔ 技能表 一致性（命令类）

跑套件时可顺带执行（一条 `game_eval`）：

```gdscript
var D := preload(String("res://scenes/battle/battle_defs.gd"))
# 只比对**同类**：技能表 source=command 的技能 ↔ 卡池 kind=command/command_x 的卡
var pool_names := {}
for c in D.POOL:
	if str(c.get("kind","")) in ["command", "command_x"]:
		pool_names[str(c["name"])] = true
var missing: Array = []
for k in D.SKILLS.keys():
	if str(D.SKILLS[k].get("source","")) == "command" and not pool_names.has(str(k)):
		missing.append(str(k))
return "指令技能无对应卡：%s" % ("无 ✅" if missing.is_empty() else str(missing))
```

**为什么只比 `command` 类**：支援 / 被动类技能**属于单位卡**（如「鼓舞」挂在叶蜂、「机场」挂在蜂巢），
它们**本来就不该出现在卡池的指令卡里** —— 早期"技能表有、卡池无"的告警正是把这两类混比所致。

**2026-08-28 实测结果（迭代005 · run_token=6）**：
```
技能表=17 条（其中指令类 11）· 卡池=17 张（其中指令卡 11）
指令技能无对应卡：无 ✅     指令卡无对应技能：无 ✅
```

## 已知坑（跑套件前先看）

| 坑 | 说明 |
|----|------|
| **进程内重复 `start_battle()`** | 见上方"铁律"：单位累积 → 同名/同格单位互抢目标 → 结果假阴（本目录套件均要求干净进程） |
| **费用上限** | 费用取 **5** 等非边界值；取 10（上限）时资源类 `+N` 会被 `clampi` 截断，把**正确行为误判为缺陷**（本迭代已误判一次） |
| **单位阵亡后取值** | 构造"非致死"场景（先把 hp 抬高），否则后续读取已移除单位的字段会运行时报错 |
| **类型推断** | `game_eval` 中 `var x := 未类型化对象的方法()` 会推断失败 → 一律写 `var x: Dictionary = ...` |
| **嵌套函数** | GDScript 的 eval 片段**不能定义函数**，用内联表达式 |
